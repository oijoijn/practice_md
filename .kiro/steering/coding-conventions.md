# コーディング規約（移植容易性重視）

この規約は、実装を**他言語（特に Go）へ入れ替えやすくする**ことを第一目的とする。
そのため「言語固有の便利機能に依存しない、素直で明示的なコード」を優先する。
迷ったら「Go に翻訳するときそのまま写せるか？」を判断基準にする。

## 1. 関数の設計

- 副作用のないロジックは**純粋関数**として切り出す。I/O（ファイル・ネットワーク・時刻取得）は関数の端に寄せ、中心のロジックは引数と戻り値だけで完結させる。
  - Go でもテストしやすく、そのまま移植できる。
- クラスのメソッドよりも、**状態を引数で受け取る関数**を優先する。状態を持つ必要がある場合のみクラス/構造体にまとめる。
  - 例: `parseConfig(raw, cwd)` のように依存を明示的に引数で渡す。グローバル状態やシングルトンに依存しない。
- 1 関数 1 責務。分岐や I/O が増えたら小さな関数に分割する。

## 2. 命名規約

- 関数名は**動詞 + 名詞**の能動形にする: `parseMarkdown`, `resolveRoute`, `generateIndexPage`, `loadConfigFile`。
- 真偽値を返す関数・変数は `is` / `has` / `should` で始める: `isMarkdownFile`, `hasError`。
- 変換系は `parse`（文字列→構造）、`generate` / `wrap`（構造→文字列）、`resolve`（入力→分類/確定値）で統一する。
- 取得系は `get`（同期・確実）、`load`（I/O を伴う）で区別する: `getContentType`（同期）／ `loadConfigFile`（ファイル読み込み）。
- 略語を避け、フルスペルで書く。Go の公開/非公開はケースで表すため、TypeScript 側でも意味が一目で分かる名前にしておく。
- 型・インターフェースは名詞（`ServerConfig`, `RouteKind`, `ParseError`）。

## 3. 戻り値とエラーの扱い（最重要）

移植時に最も差が出るのがエラー処理。**例外をコンポーネント境界で投げない**。

- 失敗し得る関数は `Result<T, E>` 型を返す。例外を throw しない。
  - Go の `(T, error)` にそのまま対応する。呼び出し側は必ず結果を検査する。
- `Result` の形は判別可能ユニオンで統一する:

  ```typescript
  export type Result<T, E> =
    | { ok: true; value: T }
    | { ok: false; error: E };
  ```

- ドメイン固有の結果型も同じ「タグ付き」形にする（`ParseResult`, `PrintResult`）。
  戻り値のバリアントを増やすときは `{ ok: true; ... }` / `{ ok: false; error }` の 2 形を保つ。
- エラーは文字列ではなく**種類を表す判別子（kind）を持つ構造体**にする:

  ```typescript
  export interface ParseError {
    kind: "null_input" | "binary_input" | "conversion_error";
    message: string;
  }
  ```

  - Go では sentinel error / error 型の判別に対応する。`kind` で分岐できるので、メッセージ文字列の比較に依存しない。
- 外部ライブラリが throw する場合は、**その関数の内側で catch し、Result に変換して返す**。例外を外へ漏らさない。
- 分類・状態を表す戻り値もタグ付きユニオンにする（`RouteKind` の `{ kind: "markdown"; filePath }` など）。Go の型スイッチに対応する。

## 4. 型の定義

- ドメイン型はすべて `types.ts` に集約し、他モジュールは型をそこから import する。
  - 移植時に「型定義ファイル＝データモデル」として最初に写せる。
- `null` / `undefined` を意味に使い分けない。「値なし」は 1 つの表現に統一する（省略可能は `?`、明示的な不在は `undefined`）。Go には `null`/`undefined` の区別がないため、片方に寄せておく。
- マジックナンバー・固定文字列は名前付き定数にする: `DEFAULT_PORT`, `DEBOUNCE_MS`, `DEFAULT_CONTENT_TYPE`, `HEARTBEAT_INTERVAL_MS`。

## 5. モジュール構成

- 1 モジュール = 1 コンポーネント（`parser`, `router`, `config`, `sse`, `watcher`, `server`）。
  - Go の 1 パッケージに対応させやすい粒度を保つ。
- モジュール間は**関数と型のみ**でやり取りし、内部実装（プライベート関数）は export しない。
- モジュールをまたぐ循環依存を作らない。共有される型は `types.ts` へ。
- エントリポイント（`index.ts` の `main()`）は「組み立て」だけを行い、ロジックを持たない。

## 6. 移植容易性のためのアンチパターン（避けること）

- 例外を制御フローに使う（throw で正常系を分岐する）。→ Result を返す。
- プロトタイプ拡張・デコレータ・複雑なジェネリック体操など、他言語に対応物がない機能への依存。
- クロージャに状態を溜め込む設計を多用する。→ 状態は明示的な構造体に持たせる。
- `any` の使用。型は明示する（`unknown` で受けて絞り込む）。
- 暗黙の型変換に依存した比較（`==`）。→ 厳密比較（`===`）を使う。

## チェックリスト（実装・レビュー時）

- [ ] 失敗し得る関数は `Result` を返しているか（throw していないか）
- [ ] エラーは `kind` 判別子を持つ構造体か
- [ ] I/O とロジックが分離されているか
- [ ] 依存は引数で明示的に渡されているか（グローバル/シングルトン非依存）
- [ ] 定数に名前が付いているか
- [ ] この関数を Go に写すとき、素直に翻訳できるか
